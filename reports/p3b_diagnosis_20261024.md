# P3-B 训练效果与六任务失败诊断

2026-10-24，基线 `5dfaef520706d57e3843f434b96ca6dbac66c059`。本轮为已有证据离线诊断，0 模型请求、0 GPU 训练、未启动远程机器，原数据、原奖励、原轨迹及运行源码锁均不改。

**结论：真实参数训练成功，但任务能力仍弱；此外，上一轮“有效评价 1/4”不能作为总体成绩。** 保存的 AppWorld 官方 TestTracker 原始结果是 Raw **0/6**、Base-SFT **1/6（16.7%）**。唯一成功来自已经用于训练的任务；内部验证和官方 dev 都是 0/2。当前没有泛化提升证据。

## 1. 确认存在的问题

### 1.1 项目评价包装层过于宽泛地排除了任务

`src/recoveragent/evaluation.py:39` 起通过 profile 观察 TestTracker；凡出现非 AssertionError，即将项目 `success` 置 null、标 `evaluation_error`。这是防止历史数据库兼容异常被当作策略失败的保守保护，但无法区分“环境损坏”和“模型未完成任务导致测试访问不到对象”。

此次两个相关任务的官方原始 `official.success` 均为 false；两模型共 12 条记录的 passes+failures 全部等于官方 num_tests，官方 tracker 已完整返回。固定官方源码 `TestTracker.__exit__` 会把测试块内异常记录为失败，`success` 根据全部测试是否通过计算。项目包装层的 null 与官方原始 false 是两个不同字段。

- `e3d6c94_3`：模型没有创建目标歌单。官方测试先发现新增歌单数量不符，后续继续访问空列表，触发 IndexError；再访问未成功赋值的局部变量，触发 UnboundLocalError。
- `68ee2c9_3`：模型没有完成文件改名/移动。官方测试后续访问本应存在的目标路径，触发 KeyError。

这些有直接业务未完成证据，不能笼统说成“模型可能做对了，只是环境坏了”。本次未发现前轮 SQLite 缺表问题的证据。我们也不因此推断所有未来非断言异常都能安全计作策略失败。

**修正报告口径**：以现有官方原始 tracker 给出六任务完整结果，同时保留项目异常标记作为诊断列。原报告、控制日志与奖励不回写；本轮也未修改运行时分类代码。原 0/4、1/4 只是排除异常标记后的条件统计，不能用 25% 表示总体成功率。实际应区分完整官方返回、业务状态触发的测试异常、数据库/加载错误、评价顶层崩溃，不能只看 Python 异常名称。

### 1.2 Student 已学会部分执行，但基础参数和证据使用仍不可靠

Base-SFT 的 6 个任务中，**5 个任务的前两轮**均调用 `api_docs__show_api_descriptions({})`，漏掉可见 Schema 中必填的 `app_name`，共 10 次；12 次参数拒绝中的另外两次分别为把登录参数放入文档查询、向搜索函数传入不支持的参数。

这不是 Harness 无故拒绝：原请求可见 Schema、解码后的原始模型 token 和执行前校验一致。每条任务仅允许两次纠正机会，所以开始两次错误后，再发生一次协议错误就结束。这个预算行为符合当前协议；问题在于模型很容易消耗完它。

现有反馈只给 `invalid_arguments`、函数名和“检查参数类型/必填字段”的通用提示，没有指明缺少哪个字段。原始非法回复只存审计、不作为合法工具消息插入历史，所以后续模型主要依赖这一通用提示。这是可以改进的反馈质量问题，但不能仅凭此次结果认定增加反馈细节一定能解决，也不应直接放开无限重试。

模型还有明确业务错误：把“我是否关注该歌手”当成“该歌手有多少粉丝”；把邮箱用户名猜成文件系统目录名；忽略已经看到的发行年份过滤条件；反复读取文档或全目录导致上下文膨胀。Harness 检查协议合法性，不负责替模型判断应删哪些歌曲或生成正确业务参数。

### 1.3 训练与部署提示存在已确认的分布差异

重新审计正式集：训练 82 轨迹中，v3/v4/v5 分别 8/11/63，B/A 分别 67/15；内部验证 13 轨迹中，v3/v4/v5 为 4/2/7，B/A 为 11/2。全部 95 条原示范都没有后来加入的 `PUBLIC HARNESS PROTOCOL v1` 提示。

本轮实际 Student 使用 execution_v5+B+当前 Harness，且会收到训练集没有示范过的纠错反馈。协议/上下文分布不同是事实，可能影响表现；**尚未做匹配提示消融，不能把它认定为唯一根因**。现有混合历史集仍是当时按规则筛选的真实成功示范，不能现在改写它或声称原数据造假。

## 2. 没有发现的训练故障，以及效果解释

- 105 次 Teacher `show_api_descriptions` 调用（train90、validation15）全部有 `app_name`，没有发现参数被漏标/错误屏蔽、目标位置错位或示范本身普遍缺参数。该结论不替代对整个训练优化目标的所有可能问题做穷尽证明。
- 原数据 manifest 仍为 `5b297cf38d7b23cb6dc02c461a0bb030c69e58d938bffda9c7569a67ad44b24c`。

正式 train loss=0.227391，最终内部 validation loss=0.164290；第50/100步内部验证 loss=0.179165/0.164495。这说明训练过程数值正常，不能直接换算成任务成功率。这里的 loss 是在真实 Teacher 历史前缀上、按样本权重计算的监督目标损失，Student 自己执行时会产生不同历史并累积错误。

**没有测 Raw 在同一完整验证集上的 loss**；短/长 smoke 使用不同样本，不能拿 smoke loss 与正式 loss 相减来宣称提升。也不能仅凭当前训练/验证 loss 判断是否过拟合。真正进入梯度更新的是 82 条完整轨迹、64 个任务、24 个家族、229776 个监督 token；95 条总集包含内部验证部分。

## 4. 建议的处理顺序（尚未修改运行行为）

1. **先修评价报告口径。** 同时保存官方 tracker 分数、测试异常和环境完整性；完整官方返回不能因为模型状态导致测试异常就直接从分母排除。对真实数据库/加载/顶层崩溃继续保留未知，不机械将所有异常变0。
2. **做具体、保守的协议反馈。** 从当前可见 Schema 返回缺少字段名、未知字段名/类型路径，例如 missing_required=[app_name]；不填参数值、不替模型选业务API、不扩大纠错预算。验证Teacher/Student一致，并独立版本化，不覆盖旧锁。
3. **先定位训练后的固定格式退化。** 用匹配部署提示的Teacher前缀，对Raw/SFT比较首轮函数和参数预测；当前只是确认五任务出现同种漏参，并未测对应logprob。先分清提示分布、采样与学习问题，不直接归因于训练太少或盲目加epoch。
4. **再规划新版本数据与基础执行验证。** 当前没有真实Harness纠错成功样本进入95条；可用真实成功的、版本匹配的正常执行/协议纠错示范补齐，保留任务/家族划分。不能用本次dev目标答案回灌训练，也不能用Harness代做年份过滤或目标选择。业务语义和长任务状态跟踪仍需模型学习。

当前不建议用放宽官方验收、自动补业务动作、仅增加上下文或直接GRPO掩盖问题。恢复学习按既定顺序，在基础执行与可用评价口径明确后推进。
